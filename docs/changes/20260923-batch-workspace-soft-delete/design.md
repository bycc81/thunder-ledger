# 批次与工作区软删除设计

## 结论

批次和工作区均为软删除：批次所有者、工作区管理员和工作区所有者可删除可访问的批次；工作区创建人可直接删除工作区，无需先删除其中的批次。删除只隐藏可见性，不清理业务记录。

## 风险等级

`L2`。涉及删除权限、数据可见性和历史记录保留。

## 产品与 UX 输入

本轮不适用。不新增页面或改变操作路径；仅修正已有删除流程的后果提示与服务端判断。

## 背景与目标

批次和工作区的删除都用于隐藏不再需要的内容，而不是清理历史数据。现有工作区删除逻辑要求先删除全部批次，且批次详情页没有删除入口，造成正常删除操作无法完成。

## 非目标

- 不物理删除批次、工作区或其采购、销售、费用、结算和审计记录。
- 不改变工作区管理员、批次所有者、编辑者和查看者的权限模型。
- 不提供删除后的恢复入口。

## 页面/API 契约

| 操作 | 权限 | 接口 | 成功结果 | 失败反馈 | 二次确认 |
|---|---|---|---|---|---|
| 删除批次 | 批次所有者；工作区管理员/所有者 | `DELETE /api/batches/:id` | 批次从列表和详情隐藏；记录保留 | 无权时 403 | 是：说明批次隐藏、已有记录保留且不可继续操作 |
| 删除工作区 | 工作区创建人 | `DELETE /api/workspaces/:id` | 工作区及其中批次从界面隐藏；记录保留 | 非创建人 403 | 是：说明工作区隐藏、已有记录保留且不可继续操作 |

- 既有定位 ID 保持不变：`batch-delete-confirm`、`workspace-delete-confirm`。
- 定位 ID 注册表：`data-ai-id-registry.md`。
- 删除工作区不会修改其中批次的 `deleted_at`；工作区被隐藏后，其批次因工作区不可访问而一并从界面隐藏。

## 方案与影响范围

- 后端工作区删除不再检查批次数；批次详情接口返回当前用户的批次角色，供详情页做安全的操作显隐。
- 前端复用既有 `DangerConfirmDialog`：批次列表的更多菜单修复 Vant `reference` 插槽；批次详情页底部增加危险操作区。

## 风险、备份与回滚

- 删除仍为软删除，业务与审计数据不执行物理清理。
- 所有删除均需前端二次确认，服务端继续校验角色，不能绕过权限。
- 若需要恢复单个批次，在确认其所属工作区仍可见后执行：`UPDATE collaboration_batches SET deleted_at = NULL WHERE id = '<batch-id>';`。
- 若需要恢复工作区执行：`UPDATE workspaces SET deleted_at = NULL WHERE id = '<workspace-id>';`；其中批次无需额外恢复，因为删除工作区不会修改批次记录。
- 不涉及数据库迁移；SQL 恢复仅由维护者在确认目标 ID 后手工执行。

## 验收标准

- 有业务记录的批次可由授权角色软删除，接口后批次不再出现在列表。
- 编辑者和查看者删除批次返回 403。
- 工作区创建人即使工作区仍有批次，也可删除工作区；工作区和其中批次均不再可见或可操作。
- 批次与工作区删除弹窗均显示已确认的后果文案。
- 批次列表的更多菜单和批次详情页的危险操作区均能发起删除。
