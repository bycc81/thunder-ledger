# 审计日志系统管理员权限修复设计

## 结论

修复 `GET /api/audit` 未复用统一工作区访问判定的问题。系统管理员对存在且未删除的工作区按 `owner` 权限读取审计日志；普通成员仍仅限工作区 `owner` 或 `admin`，编辑者和查看者继续返回 `403`。可直接进入实现，不涉及生产发布、数据迁移或权限范围扩张。

## 风险等级

`L2`。本次修改服务端授权分支，必须保证只修复系统管理员与其他工作区接口不一致的问题，不能放宽普通成员权限。

## 产品与 UX 输入

本轮不适用：不新增页面、不改变既有页面流程或交互，只修复现有 API 的服务端权限一致性。

## 背景与目标

系统管理员可以通过 `/api/workspaces` 查看全部未删除工作区，并通过统一的 `accessRole` 被视为工作区 `owner`，因此可以创建批次。`GET /api/audit` 却直接查询成员表，系统管理员未显式加入该工作区时返回 `403`，导致创建批次后工作区刷新失败。

目标是在保持审计日志仅对工作区管理者可见的前提下，使系统管理员的审计读取权限与现有工作区访问规则一致。

## 非目标

- 不改变普通 `owner`、`admin`、`editor`、`viewer` 的权限。
- 不修改工作区成员关系、批次归属、审计日志数据或数据库结构。
- 不新增前端权限绕过或更改操作记录页面。

## 当前实现与缺口

- `accessRole` 已将已认证的系统管理员映射为工作区 `owner`。
- `/api/audit` 未使用 `accessRole`，而是直接调用成员表查询，遗漏了系统管理员分支。
- 审计读取还须确认工作区 ID 合法且工作区未软删除，防止系统管理员因全局映射读取不存在或已删除工作区的历史日志。

## 页面/API 契约

本轮无页面或客户端字段变更。既有接口保持不变。

### 操作与接口边界

| 操作 | 前置条件 | 接口 | 成功结果 | 失败结果 |
|---|---|---|---|---|
| 读取工作区审计日志 | 已登录；工作区存在且未删除；系统管理员或工作区 owner/admin | `GET /api/audit?workspaceId={uuid}` | `200`，返回该工作区分页审计记录 | `403`：无工作区、非法/已删除工作区或权限不足 |

- 请求参数：既有 `workspaceId`、筛选条件与分页参数不变。
- 前端显隐不替代服务端授权：接口继续在后端校验权限。
- `data-ai-id`：本轮无页面变更，不适用。

## 方案与影响范围

1. 在审计路由中先验证 `workspaceId` 格式并确认工作区未删除。
2. 使用 `accessRole` 取得统一工作区角色，再通过现有 `canManage` 判断是否可读取审计日志。
3. 在角色回归测试中模拟未加入目标工作区的系统管理员，覆盖“创建批次后读取审计日志”场景。

影响文件：`apps/backend/src/access.ts`、`apps/backend/src/role-regression.ts`。不涉及迁移、配置、部署或前端代码。

## 风险、备份与回滚

- 授权风险：若仅改为 `accessRole` 而不验证工作区存在性，系统管理员可能读取已删除工作区日志；通过先校验未删除工作区避免。
- 普通账号风险：回归矩阵继续断言 editor/viewer 对审计接口为 `403`。
- 数据与隐私：不新增日志字段、不输出凭据或隐私数据，也不改动已有审计记录。
- 备份与迁移：无数据写入和结构变更，无需备份或迁移。
- 回滚：恢复本次两个源文件即可回到原行为；不影响数据库数据。

## 验收标准

1. 系统管理员未加入某个存在工作区时，创建批次后读取该工作区审计日志返回 `200`。
2. owner/admin 仍可读取审计日志；editor/viewer 仍返回 `403`。
3. 非法或已删除工作区 ID 仍不能读取审计日志。
4. 后端 `npm run typecheck`、`npm test` 通过。
