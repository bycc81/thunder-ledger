# 批次 0 设计记录：需求与架构冻结

## 结论

本批次只冻结业务边界和研发路线，不修改业务代码。ThunderLedger 采用模块化单体；空间是长期容器，协作批次是参与人和账务边界。

## 风险等级

`L2`。后续实现涉及账户、数据权限、财务计算和结算不可变性。

## 背景与目标

将个人售卖、共同采购、多人销售、费用垫付和最终结算整理为可追溯的领域模型，避免后续按单表 CRUD 迭代导致权限和账务口径漂移。

## 方案与边界

- 首期使用 Vue + Fastify + PostgreSQL + R2 模块化单体。
- `Workspace` 长期复用；`CollaborationBatch` 按批次定义参与人和可见范围。
- 销售人只记录收款归属；销售额进入批次公共收入池，按收益比例分配。
- 金额精确到 0.1 元，内部存储整数“角”，API 传输金额字符串。
- 首期只启用手工渠道，通过 `ChannelAdapter` 为后续平台同步预留接口。
- 结算确认后生成不可变快照，后续只能追加调整单。

## 验收标准

- 需求、路线图、架构文档均同时提供 Markdown 和 HTML（路线图、架构图）。
- 文档明确空间与批次关系、权限矩阵、公共收入池和结算公式。
- 文档内容与现有技术栈一致，且明确本批次不开发业务功能。

## 回滚与后续

本批次仅新增文档，回滚可删除本批次新增文档。进入批次 1 前，先按需求文档建立用户、空间、批次权限的数据库设计和测试计划。
