# B4.1 技术设计

以 `product-ux.md` 与 `prototype/index.html` 为产品和交互基线。采购更正使用追加历史记录，主采购记录保存当前值；受影响的已确认账单创建独立调整单，不修改原账单。

## 数据与接口

- 增加采购更正、采购更正成本承担快照、结算调整单、成员差额和转账建议表。
- `PATCH /purchases/:purchaseId` 使用 `occurredAt` 作为唯一采购时间字段，不接收 `purchasedOn`；有销售时要求 `costCorrectionReason`，返回创建的调整单数量。
- 增加调整单列表、详情和确认接口；账单详情返回关联调整单摘要。
- 结算接口不再接受或保存 `costShares`；成本承担与采购付款由成本流水自动汇总，结算请求只接收销售、费用和利润比例。
- 结算计算使用按发生时间重放的移动平均成本流水。销售成本、采购付款与成本承担构成均在销售发生时冻结为可重建快照，并计入成员净额。
- 结算成员结果先将销售额扣除费用和商品成本得到净利润，再按利润比例分配；成本承担金额作为成本回补单独计入成员结果，不再混入利润比例，也不重复叠加采购付款快照。成员净额 = 利润份额 + 成本回补 + 垫付费用 - 已收销售款。
- 采购数量更正不按单笔采购与销售绑定校验；有销售时仅以完整时间流水重放结果判断历史时点库存是否足够。
- 销售仅提供创建接口，不提供成交时间更新接口；销售时间作为成本流水事件的不可变时间。
- 销售时间一经写入 `sales.occurred_at` 即冻结；采购更正、结算调整和撤销流程均不更新该字段。

## 事务与兼容

采购行在事务中锁定；写入更正快照、更新主记录、重放后续流水与生成调整单为同一事务。重放若出现历史负库存则回滚。既有账单不回填历史直接修改，只从本次更正开始产生审计与调整记录。

采购时间统一以 UTC 保存；`purchased_on` 仅作为数据库兼容字段由采购时间派生，不进入前端/API 契约。更正态直接禁用商品、渠道和采购时间。

迁移器统一按 LF 规范化 SQL 后计算校验值；对已确认的早期开发库 002–009 校验值提供白名单兼容，未知校验值仍然阻止升级，避免掩盖迁移文件被意外修改。

## 页面/API 契约调整

- 创建账单第二步标题为“确认利润比例”；成本承担明细使用 `settlement-auto-cost-breakdown` 展示为只读结果，不提供输入框。
- `POST /settlements/preview` 与 `POST /settlements` 的请求体仅包含 `saleIds`、`expenseIds`、`profitShares`；服务端统一从销售成本分摊快照计算成本承担与实际付款构成。
- 如需改变成本承担或付款人，必须通过采购新增或采购更正流程；结算页不提供临时覆盖。
