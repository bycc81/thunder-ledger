# v1 数据库备份与隔离恢复设计

## 结论

本批次使用本地 PostgreSQL 数据库生成 custom-format 备份，并恢复到全新的临时 PostgreSQL 容器。演练只验证备份可读性、迁移记录和核心表计数，不修改源数据库。

## 风险等级

`L2`。涉及完整数据库副本、敏感数据和恢复流程，但不操作生产数据库。

## 产品与 UX 输入

本轮不适用。

## 背景与目标

当前已有 `scripts/backup-db.sh`，但缺少可重复的恢复演练、恢复后核对和结果记录。目标是证明备份文件可以在隔离环境恢复，并得到可核验的数据一致性证据。

## 非目标

- 不连接或恢复生产 Neon 数据库。
- 不覆盖现有本地 PostgreSQL 数据卷。
- 不承诺云供应商实际 RPO/RTO；本地耗时只作为参考。
- 不长期保留包含业务数据的临时备份文件。

## 方案与影响范围

- 新增 PowerShell 恢复演练脚本。
- 从当前 Compose `db` 容器执行 `pg_dump --format=custom`。
- 将备份复制到工作区临时目录，再复制到新的临时 PostgreSQL 容器。
- 使用 `pg_restore` 恢复到空数据库。
- 对比 `schema_migrations`、用户、工作区、批次、商品、采购、销售、费用和结算账单数量。
- 无论成功或失败，都停止临时容器并删除临时备份文件。

## 风险、备份与回滚

- 临时文件包含完整本地数据，脚本必须在 finally 中删除，路径必须限制在仓库 `.tmp/recovery-rehearsal`。
- 恢复目标使用独立容器和数据库，不允许指向现有 Compose 数据库。
- 源数据库只执行只读 `pg_dump` 和计数查询。
- 演练失败不对源库执行任何回滚操作。

## 验收标准

- 成功生成非空 custom-format 备份。
- 新临时数据库可以完整 `pg_restore`。
- 迁移版本数量和核心表计数与源库一致。
- 临时容器和备份文件在结束后被清理。
- 记录演练耗时和未覆盖的生产风险。
