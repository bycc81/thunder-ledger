# 产品与 UX 定义：B2 库存、采购来源与成本

## 结论与确认

本变更补齐 B3 所需的库存能力：在协作批次内记录每次采购，并按“批次 × 商品”合并显示可卖数量和成本。采购来源使用工作区可复用的手工渠道名册；卖出时不追溯具体采购来源。可运行原型位于 [prototype/index.html](prototype/index.html)，不连接真实 API。

已确认的页面方向是从批次详情进入“库存”，先看商品汇总，进入详情查看采购明细；新增采购选择已有商品、渠道和付款人。原型确认后才能进入技术设计与实现。

## 交付节奏

本 B2 库存模块只分为两个可独立验收的小阶段，不再细拆：

1. **B2-1 采购与成本**：手工渠道名册、采购记录、付款人、必填成本承担、库存汇总与采购详情。完成后用户可正确登记“买了什么、谁付款、谁承担成本”，并查看合并后的可卖数量和总成本。**已于 2026-09-08 验收通过。**
2. **B2-2 库存维护**：采购编辑、商品损坏或丢失时减少库存、操作记录与权限反馈。完成后库存数量可被安全维护，为 B3 销售扣库存做好准备。

两个阶段均验收完成后，才开始 B3 的上架、销售和费用开发；B3 不再补做 B2 遗留能力。

## 用户、问题与范围

- 目标用户/角色：批次 owner、editor、viewer；工作区 owner/admin 依现有授权拥有批次管理能力。
- 使用场景与触发入口：共同经营小卡时，成员分别从不同渠道采购同一种商品，但销售时无法识别具体来源。
- 当前问题：现有商品资料不绑定批次，没有库存、采购成本、付款人或采购来源，无法安全支撑销售扣库和后续结算。
- 产品目标：记录采购来源、谁付款以及谁承担成本，同时让同一批次内同商品合并在一起卖。
- 可观察结果：A 从渠道 1 录入 1 张/60 元、B 从渠道 2 录入 1 张/70 元后，库存显示 2 张/130 元；后续销售只扣该商品汇总库存。
- 本次做什么：工作区手工渠道名册、采购记录、付款人、必填的成本承担、库存汇总与详情、未卖出前编辑、商品损坏或丢失时减少库存、权限与操作记录体验。
- 本次不做：上架、销售、费用、收益分配、结算、外部渠道账号或自动同步。

## 用户流程、规则与场景

### 用户主流程

~~~text
批次详情 → 库存 → 商品汇总
  ├─ 打开商品库存详情 → 查看采购明细与可售数量
  ├─ 新增采购 → 选择商品、渠道、付款人 → 填写数量/总成本和每人承担的成本 → 保存
  └─ 商品损坏或丢失 → 填写数量与原因 → 确认减少库存
~~~

### 业务规则与权限

- 采购记录属于一个批次和一个既有商品；渠道名称必填、来源链接和备注可选；付款人必须是该批次参与人。
- 每次采购必须填写“谁承担这笔成本”：至少一位批次参与人及各自承担金额，合计必须等于这笔采购的总成本。系统不按实际付款比例预填，也不猜测分摊方式。
- “谁付款”和“谁承担成本”是两件事：例如 A 实际付 60 元、B 实际付 70 元，共 130 元；可以填写 A、B 各承担 65 元，也可以按双方确认的其他金额填写，只要合计 130 元。
- 工作区维护可复用的手工渠道名册；有编辑权的用户可在采购表单中新增渠道，后续 B3 上架直接复用。
- 库存按“批次 × 商品”汇总，数量为正整数；金额精确到 0.1 元。采购总成本可不同，销售不选择采购来源。
- 后续卖出或减少库存时，系统把同一商品的总成本平均分到卖出的数量上；若出现 0.1 元零头，最后一次卖出或减少的商品承担零头，保证总成本不差钱。
- 尚未卖出时，采购数量和成本可以直接编辑或删除；已经卖出后，数量不能直接改，只能在商品损坏或丢失时减少库存；采购成本仍可直接改正，但必须填写原因并留下操作记录，结算确认前会重新计算成本。
- 减少库存必须填写原因，且不能让可卖数量变成负数；对应成本会计入这批商品已经消耗的成本。
- owner/editor 可新增、编辑和减少库存；viewer 只读。服务端权限以后续技术设计为准，前端隐藏不等于真正有权限。

### 需求场景

#### Requirement: 合并在一起卖的库存

系统 SHALL 将同一批次、同一商品的多条采购记录合并为一个可卖库存，不要求卖出时追溯采购渠道。

#### Scenario: 两位成员从不同渠道采购

- **WHEN** A 从渠道 1 录入 1 张、总成本 60 元，B 从渠道 2 录入 1 张、总成本 70 元
- **THEN** 系统显示该批次商品可售数量为 2、采购总成本为 130 元，并保留两位付款人和渠道来源

#### Requirement: 采购时确认成本承担

系统 SHALL 要求每次采购保存成本由哪些批次参与人承担，以及每人承担金额；承担金额合计必须等于采购总成本。

#### Scenario: 实际付款与成本承担不同

- **WHEN** A、B 实际分别付款 60 元和 70 元，录入的采购总成本为 130 元
- **THEN** 用户必须明确填写成本承担，例如 A、B 各 65 元；系统不自动按 60/70 元填写

#### Requirement: 卖出前可修改，卖出后保留原记录

系统 SHALL 允许在未卖出时直接修改采购记录；卖出后阻止直接改变数量，只能通过“商品损坏或丢失”减少库存。

#### Scenario: 销售后发现一张小卡损坏

- **WHEN** 商品已经卖出过，编辑者登记 1 张损坏并填写原因
- **THEN** 系统新增一条减少库存记录、减少可卖数量并保留原采购和销售记录

## 页面与交互规格

### 页面地图

~~~text
批次详情
  └─ 库存
      ├─ 商品库存汇总
      │   └─ 新增采购
      └─ 商品库存详情
          ├─ 采购明细
          ├─ 编辑采购
          └─ 减少库存确认
~~~

### 库存汇总

- 核心任务：识别批次内可销售的商品与数量，进入详情或新增采购。
- 信息层级：批次名称 → 可售库存总览 → 商品列表 → 新增采购。
- 主操作：新增采购；空状态不重复放置按钮。
- 列表项：商品封面/名称、可售数量、采购总成本、采购明细数量。

### 新增/编辑采购

- 核心任务：将一笔真实采购归入批次商品库存。
- 字段：商品（必填）、渠道（必填，可新增）、付款人（必填）、数量（必填正整数）、总成本（必填，非负且最多一位小数）、成本由谁承担（必填，可添加多位批次参与人，金额合计必须等于总成本）、采购日期（必填）、来源链接和备注（可选）。
- 主操作：保存采购；未保存返回需要确认。
- 编辑限制：销售前可编辑数量/成本；销售后数量只读，成本更正要求填写原因。

### 商品库存详情

- 核心任务：阅读合并后的库存数量、成本和来源记录，并在需要时减少库存。
- 信息层级：商品名称和可卖数量 → 成本摘要 → 采购记录 → 减少库存记录。
- 危险操作：商品损坏或丢失收在库存详情右上角“更多操作”内；弹窗必须显示减少数量、原因和确认按钮。

## 状态、响应式与验收

| 状态 | 页面表现 | 可执行操作 |
|---|---|---|
| Loading | 商品行骨架，保留批次上下文 | 禁用新增与减少库存 |
| Empty | “本批次还没有库存”说明 | 有写权限者从标题新增采购 |
| Error | 可理解的失败提示和重试 | 重试，不清空表单 |
| 无权限 | 只读说明，不显示写入口 | 查看已授权库存 |
| Disabled | 保存、减少库存或加载中禁用对应控件 | 等待或取消 |
| Success | Toast 后刷新库存记录 | 查看更新后的数量与明细 |

- 目标视口：390×844、430×932；单列列表和表单，触控目标至少 44px。
- 复用 MobileShell、批次详情、Vant NavBar/Cell/Field/Form/Popup/Dialog/Toast 与现有主题变量；不引入第二套组件库。
- 视觉方向：白色列表表面、浅灰画布、深靛蓝主操作、红色减少库存操作；不用宽表格、卡片墙或渐变。
- 原型：[prototype/index.html](prototype/index.html)。

### 页面验收

- [ ] 用户能从批次详情进入库存并找到新增采购。
- [ ] 两个不同渠道、付款人的采购明细会汇总为同一商品库存池。
- [ ] 每笔采购均必须填写成本由谁承担，且承担金额合计与采购总成本一致；系统不自动按付款金额填写。
- [ ] 卖出前编辑与卖出后减少库存的边界清楚可见。
- [ ] Loading、Empty、Error、无权限、Disabled、Success 可见。
- [ ] 原型的关键业务节点已登记稳定 data-ai-id。
- [ ] 用户已直接打开原型确认页面结构、主流程和关键交互。
