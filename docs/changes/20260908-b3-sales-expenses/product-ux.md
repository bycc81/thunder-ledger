# 产品与 UX 定义：B3 交易与费用

## 结论与确认

B3 在已完成 B2 库存前置能力后，只为批次提供销售和直接费用记录。批次详情直接进入“交易”页，交易页以“销售 / 费用”分栏切换；不开发上架页面或上架关联。

销售只从“批次 × 商品”合并后的库存扣减，不要求识别采购来源。采购付款人和卖出人可以不同；但谁卖出，销售款就记在谁名下，不另选收款人。收入仍先放进批次公共收入；怎么分留待 B4。可运行原型位于 [prototype/index.html](prototype/index.html)，不连接真实 API。

## 用户、问题与范围

- 目标用户/角色：批次 owner、editor、viewer；工作区 owner/admin 依现有批次授权拥有管理能力。
- 使用场景与触发入口：成员在手工渠道发布小卡，成交后记录卖出人和邮费等直接费用；卖出人就是收款人。
- 当前问题：商品已有资料但没有上架状态、销售记录、谁收款和卖货相关费用，库存与后续结算无法衔接。
- 产品目标：以最少步骤记录真实成交和费用，保证库存不超卖、人员归属可追溯，并让销售与费用可并列查阅。
- 可观察结果：销售保存后可卖库存减少；A 采购、B 卖出时，采购记录保留 A 为付款人，销售记录显示 B 卖出并收款；邮费可关联销售或仅关联批次。
- 本次做什么：交易页、卖出后减少库存、可关联销售的费用、撤销并重新填写与权限反馈。
- 本次不做：上架、外部订单同步、支付/物流接入、自动抓图、利润分配、阶段性结账页面、最终结账页面、批量导入导出。

## 用户流程、规则与场景

### 用户主流程

~~~text
批次详情
  └─ 交易 → [销售 | 费用]
      ├─ 销售 → 选择商品与数量 → 录入成交价、卖出人 → 减少库存
      └─ 费用 → 选择邮费或自定义类型 → 录入金额、付款人 → 可选关联销售
~~~

### 业务规则与权限

- 销售数量为正整数且不超过当前可卖库存；保存时同时写入销售记录和减少库存。卖出人必须是批次参与人；销售款固定记在卖出人名下，页面不提供另选收款人的字段。
- 同一商品合并后，系统把总成本平均分到卖出的数量上；销售表单不选择采购渠道。若出现 0.1 元零头，最后一次卖出或减少的商品承担零头。采购成本在 B4 结算确认前改正时，系统按发生时间重新计算该商品已卖出/已减少部分的成本。
- B2 采购时填写的“成本由谁承担”是后续结账的初始建议。B4 每次阶段性结账都先带出该建议，用户可调整各人的承担额；确认后的承担额必须保存为本次结账结果的一部分，不覆盖原采购记录，但会作为最终结账的正式计算依据。
- 费用类型默认“邮费”，也允许填写自定义名称；金额精确到 0.1 元；付款人必须是批次参与人；费用可选关联本批次一笔销售。
- 销售或费用填错时不直接编辑或删除：用户说明原因后“撤销这笔记录”，系统保留原记录并新增一条抵消记录；撤销销售会把数量还回库存，随后再填写正确销售。
- owner/editor 可写，viewer 只读；每次新增、改正和撤销都会保留操作记录。

### 为阶段性结账保留的规则（B4 实现）

- 阶段性结账按销售记录选择：用户从尚未结账的销售中选一笔或多笔，系统只计算这些销售及其已关联的费用。未关联销售的批次费用由用户在结账时另行选择是否纳入。
- 系统先按所选销售的数量算出对应商品成本，再按采购时记录的成本承担方式，给出每位成员应承担的建议金额。用户必须在本次结账中确认，也可以改成新的承担金额；所有人承担金额合计必须等于本次销售对应成本。
- 确认后生成不可修改的结账结果，其中保存所选销售、纳入费用、各成员最终确认的成本承担额和本次应收应付；并把所选销售标记为“已结账/已闭环”。这些销售不再出现在下一次可选列表中，不能直接修改、撤销或重新结账；发现错误只能在后续通过调整记录处理。
- 最终结账汇总所有已确认的阶段结账结果，并使用其中最终确认的成本承担额计算总应收应付，绝不回退为采购时的初始建议。尚未结账的销售才从采购记录带出建议，供用户确认或修改后纳入新的结账结果。

示例：两张小卡总成本 130 元，采购时确认 A、B 各承担 65 元。先卖出一张并结账时，对应成本为 65 元，系统建议 A、B 各承担 32.5 元；用户确认改为 A 承担 30 元、B 承担 35 元后，这个结果会永久保存在第一张的结账记录中。卖出第二张时，系统把采购记录中的 A、B 各 32.5 元作为建议；用户确认后，最终结账汇总两次已确认的承担额（第一张 A 30/B 35，加上第二张实际确认额），不会把第一张重新按 32.5/32.5 计算。

### 需求场景

#### Requirement: 销售与采购来源解耦

系统 SHALL 从批次商品合并后的库存减少销售数量，不要求操作人选择具体采购渠道或付款人。

#### Scenario: 不可辨认采购来源的小卡成交

- **WHEN** 两张同商品小卡分别由 A、B 从不同渠道采购后，任一成员记录卖出 1 张
- **THEN** 系统只减少该商品汇总可卖数量，成交价和卖出人会保存，不要求判断售出的是哪一条采购记录

#### Requirement: 采购付款人和卖出人可以不同

系统 SHALL 允许采购付款人与卖出人为不同批次参与人；每笔销售的收款归属固定等于卖出人。

#### Scenario: A 采购，B 卖出

- **WHEN** A 的采购记录已存在，B 填写一笔销售并保存
- **THEN** 采购记录显示 A 为付款人；交易列表显示 B 卖出并收款；销售收入进入批次公共池，不在本期直接分配收益

#### Requirement: 可追溯的交易更正

系统 SHALL 以“撤销并重新填写”的方式改正销售和费用，不覆盖原记录。

#### Scenario: 成交价录错

- **WHEN** editor 撤销一笔销售并填写原因
- **THEN** 系统保留原销售和撤销记录、把数量还回库存，并允许录入正确销售

#### Requirement: 按销售记录阶段性结账

系统 SHALL 让用户选择尚未结账的销售记录完成一次阶段性结账；确认后，所选销售成为不可直接修改的已结账记录。

#### Scenario: 先结账已卖出的一张小卡

- **WHEN** 用户选择一笔尚未结账的销售，并确认该销售对应的成本承担金额
- **THEN** 系统生成该笔销售的结账结果、将其标记为已结账，并且下一次结账不再重复计算这笔销售

## 页面与交互规格

### 页面地图

~~~text
批次详情
  └─ 交易
      ├─ 销售列表 → 记录销售 → 撤销销售后重新填写
      └─ 费用列表 → 记录费用 → 撤销费用后重新填写
~~~

### 交易页（已确认方案 1）

- 核心任务：在一个批次上下文内切换查阅销售和费用，并完成对应录入。
- 信息层级：批次名称 → “销售/费用”分栏 → 当前记录列表 → 当前栏的新增操作。
- 销售表单：商品、可卖数量提示、数量、成交价、卖出人、成交时间、备注；销售款自动记在卖出人名下。
- 费用表单：类型（邮费预置或自定义）、金额、付款人、发生时间、可选关联销售、备注。
- 危险操作：撤销销售或费用都需二次确认、原因和清楚说明会发生什么。

## 状态、响应式与验收

| 状态 | 页面表现 | 可执行操作 |
|---|---|---|
| Loading | 上架行或交易行骨架，保留批次名与分栏 | 禁用对应新增 |
| Empty | 当前栏无上架/销售/费用说明 | 有写权限者从标题新增 |
| Error | 当前页面或分栏失败提示和重试 | 重试，保留表单输入 |
| 无权限 | 只读说明，不显示新增或撤销 | 阅读有权限查看的记录 |
| Disabled | 提交、撤销、库存校验或加载中禁用控件 | 等待或取消 |
| Success | Toast 并刷新库存/当前列表 | 查看更新后的记录 |

- 目标视口：390×844、430×932；交易分栏固定在内容顶部，单列列表与表单，触控目标至少 44px。
- 复用现有 MobileShell、批次详情、Vant NavBar/Tab/Cell/Field/Form/Popup/Dialog/Toast；不新增 UI 框架。
- 视觉方向：销售和费用使用相邻列表；金额、人员和状态有清楚文字标签，不以颜色单独表达状态；撤销使用红色并置于主操作之外。
- 原型：[prototype/index.html](prototype/index.html)。

- [ ] 采购付款人与卖出人可以不同，且销售款始终自动记在卖出人名下。
