# ThunderLedger AI 开发流程

本流程面向单人维护、低并发的经营管理后台。目标是快速交付，同时保证认证、数据、部署和界面质量。

## 1. 风险分级

| 等级 | 范围 | 最低要求 |
|---|---|---|
| L0 | 文档、注释、样式、低风险脚本 | 说明目的，完成静态检查或人工自检 |
| L1 | 普通页面、CRUD、API、列表、表单和交互 | 简短变更说明；运行相关 typecheck/test/build |
| L2 | 登录权限、数据库结构、收益计算、敏感数据、安全策略、部署和不可逆操作 | 先写设计与验收记录；专项测试；生产/不可逆操作前用户确认 |

无法判断时按更高等级处理。风险等级不是审批层级；默认由开发者完成设计、实现、测试和自审。

## 2. 开始任务

先用几句话写清：目标、非目标、影响范围、风险等级和验收结果。只读任务无需创建变更文档。

按需读取：

- `AGENTS.md`
- 本文
- 当前模块附近的 README、类型、接口、迁移和测试
- 前端任务必须先读取并遵循 `docs/standards/frontend/frontend-guidelines.md`，再修改 `apps/web` 中的页面、组件、路由或样式。
- 部署任务读取 `docs/deployment.md`
- 安全任务读取 `docs/standards/security.md`

不要读取或引用已不存在的旧平台计划、专属协议设计或旧审批记录。

## 3. 设计与实现

- L0：直接修改，保持范围小，完成自检。
- L1：先写简短变更说明（目标、影响、验收），再实现；必要时补测试。
- L2：使用 `docs/standards/change-templates/design.md` 写设计记录，并用 `docs/standards/change-templates/test-plan.md` 列出验证；明确数据流、权限、迁移、回滚和残留风险。

实现时优先复用现有代码和契约，不为了未来场景提前引入服务、队列或复杂抽象。新增 SQL 必须有清晰的中文注释、表/字段说明和可重复迁移；敏感值不得写入代码或文档示例。

## 4. 验收与验证

先定义正确结果、不能破坏的行为和验证方式，再编码。按影响范围选择最小验证：

- 后端：`npm run typecheck`、`npm test`
- 前端：`npm run typecheck`、`npm run build`
- 数据库：`npm run db:check`，涉及迁移时再执行受控 migration 检查
- 容器/部署：`docker compose config`、`docker compose build`、健康检查
- 页面交互：补目标页面人工检查或可复现步骤；构建通过不等于交互正确

测试失败时可自动修复并重跑相关命令；连续三轮失败就停止自动修复，记录原因和替代验证。不要机械运行与改动无关的全量检查。

## 5. 高风险确认

涉及生产发布、删除/重置数据、不可逆迁移、权限放开、收益规则或安全策略生效时，先停在执行前，把影响、备份/回滚和验证结果告诉用户，获得明确确认后再执行。普通本地开发不等待额外审批。

## 6. 交付自审

交付前确认：目标和非目标清楚；风险等级合理；验收证据已完成；密钥和隐私未泄露；文档路径和命令有效；未验证项和残留风险已记录。

最终输出固定包含：

1. 风险等级及理由。
2. 改动摘要及原因。
3. 实际执行的验证命令和结果。
4. 未验证项、残留风险和需要用户确认的动作。
5. 更新的文档或变更记录。

## 7. 禁止事项

- 不把未实现的专属平台组件或高并发架构写成当前系统要求。
- 不提交密码、Token、连接串或真实用户隐私。
- 不在没有设计和确认的情况下执行生产或不可逆数据操作。
- 不把 typecheck/build 结果冒充完整业务验收。
